## 1. 核心背景与灾难性反面典型 (Context & The "Overwrite Trap")

在 STM32CubeMX + 嵌入式 IDE (Keil/CLion/VSCode) 的协同开发中，最危险的隐蔽缺陷之一是**“源码单向打补丁，`.ioc` 原型脱节失步”**：

```
┌─────────────────────────┐          GENERATE CODE           ┌─────────────────────────┐
│   Remote_Control.ioc    │ ───────────────────────────────> │  Core/Src/{gpio,i2c}.c  │
│ (按键 NOPULL, I2C NOPULL)│    [瞬间抹除所有手工补丁!]       │ (手工后置打补丁: PULLUP)  │
└─────────────────────────┘                                  └─────────────────────────┘
             ▲                                                            │
             │                     反向同步严重缺失                        │
             └────────────────────────────────────────────────────────────┘
```

### 致命后果：
1. **外设总线瞬间瘫痪**：开发者在 `i2c.c` 中手工将 PB8/PB9 改为 `GPIO_PULLUP`，但 `.ioc` 保持默认 `NOPULL`。某天用户在 CubeMX 调整其他引脚并点击 **GENERATE CODE**，I2C 引脚立即退化为悬空开漏，总线立刻死锁。
2. **按键矩阵悬空乱跳**：硬件按键直连 GND 无外置上拉，代码靠在 `bsp_gpio.c` 中二次初始化覆盖补救。一旦系统时序调整或外设重构，未初始化的浮空引脚引发中断风暴与按键误触发。
3. **时钟树配置回退**：手改 `SystemClock_Config()` 分频参数，未同步 `.ioc`，重新生成代码后系统主频缩水或超频违规。

## 2. CubeMX .ioc 强同步与防覆写失步免疫法则 (IOC Dual-Directional Synchronization)

为确保工程具备**“抗全盘重新生成免疫力” (Overwrite Immunity)**，所有工程师与 AI Agent 必须恪守以下法则：

### 2.1 原型即真理原则 (The IOC as Single Configuration Truth)
* **电气属性进 .ioc**：所有片上 GPIO 的电气属性（`Pull-Up`、`Pull-Down`、`Open-Drain`、`Speed`）、外设模式（如 SPI 全双工 vs 单线）、中断优先级（NVIC Priority），**必须直接在 `.ioc` 文件中配置落盘**。
* **时钟树进 .ioc**：外部晶振频率（`HSE_VALUE`）、主 PLL 分频倍频系数（$M, N, P, Q$）、总线分频（`HCLK`, `PCLK1`, `PCLK2`）必须在 `.ioc` 中通过时钟求解器锁定，严禁仅在 `main.c` 中手工私自修改。

### 2.2 应急补丁双向闭环 SOP
若在现场带板调试中，因排查硬件临时在 C 代码中重载了寄存器配置：
1. **步骤 1 (现场验证)**：在 `Firmware/BSP/` 隔离层中完成重载验证；
2. **步骤 2 (反向固化)**：验证通过后，**必须在当前会话的同一个交付周期内**，反向编辑或指导修改 `[Project].ioc` 对应字段；
3. **步骤 3 (无损验证)**：在 CubeMX 中重新生成代码，确保生成的 `Core/Src/` 代码天生具备正确电气参数，验证工程构建 0 报错。

## 3. 硬件晶振与时钟链“真理源”三方交叉核验协议 (Clock Triangulation Protocol)

在分析或配置 MCU 时钟系统时，严禁轻信单一文档陈旧描述，必须执行三方三角交叉核验：

$$\text{时钟真理源} = \text{实物 BOM 丝印型号} \cap \text{CubeMX .ioc 参数} \cap \text{运行代码寄存器 (PLLM)}$$

```
                            [实物 BOM 丝印]
                           (如: RL080001700 = 8.000MHz)
                                 /      \
                                /        \
                               /          \
                              ▼            ▼
                   [CubeMX .ioc] <──────> [实效代码寄存器]
             (RCC.HSE_VALUE=8000000)     (PLLM = 8, SYSCLK = 168M)
```

### 违规排查守则：
* 当文档记载 25MHz，而 BOM 丝印或实效代码为 8MHz 时，**必须以实物为最高权威**，禁止无端要求用户“将正确的 8MHz 改为错误的 25MHz”；
* 必须在发现偏差时立即在 `HARDWARE_SPEC.md` 与 `SOFTWARE_SPEC.md` 中完成统一勘误。

## 4. 过渡期调试脚手架即时物理拆除规约 (Scaffolding Deconstruction Standard)

在带板联调阶段，常因硬件不确定性引入辅助诊断脚手架（如 7 种屏幕尺寸轮播、多驱动对比探测、连续刷屏测试帧）。

### 4.1 即时物理拆除触发条件
当发生以下任一里程碑事件时，过渡期脚手架生命周期立即终止：
1. **硬件规格已判定**：用户明确告知屏幕驱动芯片、屏幕物理尺寸与贴合方向；
2. **用户明确下达减法指令**：如“*把其他模式删掉*”、“*只保留竖屏*”；
3. **固件转入生产/仪表盘交付态**。

### 4.2 物理拆除标准清单 (The Pruning Checklist)
* **数据表与结构体物理删除**：彻底删除过渡期的尺寸数组（如 `s_res_modes[]`）、临时测试参数表；
* **测试函数物理删除**：彻底删除轮播引擎、测试切屏函数（如 `Render_ResolutionTest()`）；
* **通信协议分支收敛**：上位机与单片机通信协议中，剔除多余的测试模式枚举，仅保留必要的基础控制指令；
* **环境解耦**：彻底清除屏幕 UI 或调试日志中硬编码的宿主机环境字符串（如特定 `COM5` 编号）；
* **容量与行数双重核验**：拆除后重新编译，核对 Flash/RAM 占用下降，且单文件严格控制在 400 行以内。

## 5. 外设驱动单文件 400 行解耦范式 (Driver Decoupling Pattern)

针对彩色 TFT、OLED、复杂传感器驱动中大量初始化寄存器配置序列占用篇幅的痛点：
* **序列外置**：若驱动初始化参数表长达 50 行以上，必须将其剥离至 `[driver]_cfg.h`，以 `const uint8_t` 表驱动方式存储于 Flash (RO-data)；
* **主逻辑紧凑**：驱动主 `.c` 文件只保留窗口裁剪、数据推流、基础几何与文本绘制，总体行数严格控制在 **200 ~ 300 行**，彻底规避突破 400 行军规。
